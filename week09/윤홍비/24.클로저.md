### 클로저란

- 클로저는 자바스크립트 고유의 개념이 아니라 **함수를 일급 객체로 취급하는 함수형 프로그래밍 언어에서 사용되는 중요한 특성**이다. ([18장](../../week05/윤홍비/18.함수와_일급_객체.md#일급-객체))
- MDN에서는 클로저를 다음과 같이 정의한다.
  - > 클로저는 함수와 그 함수가 선언된 렉시컬 환경과의 조합이다.
  - 여기서 "함수가 선언된 렉시컬 환경"이 핵심이다.
- 다음 예제를 통해 살펴보자.
  - ```javascript
    const x = 1;

    function outerFunc() {
      const x = 10;

      function innerFunc() {
        console.log(x); // 10
      }

      innerFunc();
    }

    outerFunc();
    ```
  - `innerFunc`는 `outerFunc` 내부에서 정의된 **중첩 함수**다. ([12장](../../week05/윤홍비/12.함수.md#중첩-함수))
  - 따라서 상위 스코프인 `outerFunc`의 `x`를 참조할 수 있다.
- 만약 `innerFunc`가 `outerFunc` 내부에서 정의되지 않았다면 상위 스코프가 달라진다.
  - ```javascript
    const x = 1;

    function outerFunc() {
      const x = 10;
      innerFunc(); // 1 (전역의 x를 참조한다)
    }

    function innerFunc() {
      console.log(x);
    }

    outerFunc();
    ```
  - `innerFunc`는 전역에서 정의되었으므로 상위 스코프가 전역이다.
  - 따라서 `outerFunc`의 `x`를 참조할 수 없다.
- 이처럼 **함수가 어디서 호출되었는지가 아니라 어디서 정의되었는지에 따라 상위 스코프가 결정되는 것**을 렉시컬 스코프라 한다. ([13장](../../week05/윤홍비/13.스코프.md#렉시컬-스코프))

### 렉시컬 스코프

- 자바스크립트 엔진은 함수를 어디서 호출했는지가 아니라 **함수를 어디에 정의했는지에 따라 상위 스코프를 결정**한다.
  - 이를 **렉시컬 스코프(정적 스코프)** 라 한다.
- 23장에서 살펴봤듯이 스코프의 실체는 **실행 컨텍스트의 렉시컬 환경**이다. ([23장](./23.실행컨텍스트.md#렉시컬-환경))
  - 렉시컬 환경은 자신의 "외부 렉시컬 환경에 대한 참조"를 통해 상위 렉시컬 환경과 연결된다.
  - 이것이 바로 **스코프 체인**이다.
- 따라서 렉시컬 스코프를 정확히 표현하면 다음과 같다.
  - > 함수의 상위 스코프는 **함수 정의가 평가되는 시점**에 함수가 위치하는 환경의 렉시컬 환경이다.
  - 즉 상위 스코프에 대한 참조는 함수 정의가 평가되는 시점에 **정적으로 결정**된다.

    ```mermaid
    flowchart TB
        DEF["함수 정의 시점"]
        CALL["함수 호출 시점"]
        SCOPE["상위 스코프 결정<br/>(렉시컬 스코프, 변하지 않는다)"]
        THIS["this 바인딩 결정<br/>(호출 방식에 따라 달라진다)"]

        DEF ==> SCOPE
        CALL ==> THIS
    ```

  - this 바인딩과 결정 시기가 다르다는 점을 다시 확인할 수 있다. ([22장](../../week08/윤홍비/22.this.md#함수-호출-방식과-this-바인딩))

### 함수 객체의 내부 슬롯 [[Environment]]

- 렉시컬 스코프가 가능하려면 함수는 **자신이 정의된 환경을 기억하고 있어야 한다**.
  - 호출되는 위치와 정의된 위치는 다를 수 있기 때문이다.
- 이를 위해 함수는 자신의 내부 슬롯 **`[[Environment]]`에 자신이 정의된 환경, 즉 상위 스코프의 참조를 저장**한다.
  - 함수 정의가 평가되어 함수 객체를 생성할 때 저장된다.
  - 저장된 값은 **함수 객체가 존재하는 한 유지**된다.
- 함수가 호출되면 함수 실행 컨텍스트가 생성되고, **`[[Environment]]`에 저장된 참조가 "외부 렉시컬 환경에 대한 참조"에 할당**된다. ([23장](./23.실행컨텍스트.md#4-foo-함수-코드-평가))

    ```mermaid
    flowchart TB
        subgraph S1["① 함수 정의가 평가될 때 (저장)"]
            direction LR
            OBJ["innerFunc 함수 객체<br/>[[Environment]]"]
            OLE["outerFunc의 렉시컬 환경"]
            OBJ ==>|"상위 스코프를 저장"| OLE
        end

        subgraph S2["② 함수가 호출될 때 (복원)"]
            direction LR
            CTX["innerFunc 실행 컨텍스트<br/>렉시컬 환경의 Outer"]
            SAVED["innerFunc.[[Environment]]"]
            CTX ==>|"저장된 값을 할당"| SAVED
        end

        S1 ==> S2
    ```

- 즉 **함수 객체가 자신의 상위 스코프를 들고 다니는 구조**다.
  - ```javascript
    const x = 1;

    function foo() {
      const x = 10;

      // bar의 [[Environment]]는 전역 렉시컬 환경이다 (전역에서 정의되었으므로)
      bar();
    }

    function bar() {
      console.log(x); // 1
    }

    foo(); // 1
    bar(); // 1
    ```
  - `bar`는 어디서 호출되든 `[[Environment]]`가 전역 렉시컬 환경이므로 항상 `1`을 출력한다.

### 렉시컬 환경과 클로저

- 외부 함수보다 **중첩 함수가 더 오래 유지되는 경우** 중첩 함수는 이미 생명 주기가 종료한 외부 함수의 변수를 참조할 수 있다.
  - 이러한 중첩 함수를 **클로저(closure)** 라 한다.
  - ```javascript
    const x = 1;

    function outer() {
      const x = 10;
      const inner = function () {
        console.log(x);
      };
      return inner; // 중첩 함수를 반환한다
    }

    // outer 함수를 호출하면 중첩 함수 inner를 반환한다
    // 그리고 outer 함수의 실행 컨텍스트는 실행 컨텍스트 스택에서 제거된다
    const innerFunc = outer();
    innerFunc(); // 10
    ```
- `outer`가 종료되면 실행 컨텍스트 스택에서 **제거**된다.
  - 따라서 `outer`의 지역 변수 `x`도 생명 주기를 마감한 것처럼 보인다. ([14장](../../week06/윤홍비/14.전역변수의_문제점.md#지역-변수의-생명-주기))
  - 그런데 `innerFunc()`를 호출하면 `10`이 출력된다.
- **이미 종료된 함수의 지역 변수가 어떻게 동작하는 것일까?**
  - `outer` 함수의 **실행 컨텍스트는 제거되지만 렉시컬 환경은 소멸하지 않는다**.
  - `inner` 함수의 `[[Environment]]`가 `outer`의 렉시컬 환경을 **참조하고 있기 때문**이다.
  - 참조되고 있는 객체는 **가비지 컬렉션의 대상이 되지 않는다**. ([11장](../../week04/윤홍비/11.원시값과_객체의_비교.md))

    ```mermaid
    flowchart LR
        subgraph STACK["실행 컨텍스트 스택"]
            direction TB
            G["전역"]
            GONE["outer 실행 컨텍스트<br/>(반환과 함께 제거되었다)"]
        end

        subgraph HEAP["힙 (Heap)"]
            direction TB
            OLE["outer의 렉시컬 환경<br/>x: 10<br/>Outer → 전역 렉시컬 환경"]
            FN["inner 함수 객체<br/>[[Environment]]"]
        end

        IF["innerFunc 변수"]

        FN ==>|"참조하고 있다"| OLE
        IF ==>|"참조하고 있다"| FN

        GONE -.->|"제거되어도 렉시컬 환경은 남는다"| OLE
    ```

  - 실행 컨텍스트는 제거되었지만 **렉시컬 환경은 참조되고 있으므로 메모리에 남아있다**.
- 이처럼 **외부 함수의 렉시컬 환경을 기억하는 함수**가 클로저다.

#### 클로저가 아닌 경우

- 이론적으로는 모든 함수가 상위 스코프를 기억하므로 클로저다.
  - 하지만 다음과 같은 경우는 일반적으로 클로저라 하지 않는다.

##### 1. 상위 스코프의 식별자를 참조하지 않는 경우

- ```javascript
  function foo() {
    const x = 1;
    const y = 2;

    // 상위 스코프의 식별자를 참조하지 않는다
    function bar() {
      const z = 3;
      console.log(z);
    }

    return bar;
  }

  const bar = foo();
  bar(); // 3
  ```
- 상위 스코프의 어떤 식별자도 참조하지 않으므로 **대부분의 모던 엔진은 최적화를 통해 상위 스코프를 기억하지 않는다**.
  - 따라서 클로저라고 할 수 없다.

##### 2. 외부 함수보다 생명 주기가 짧은 경우

- ```javascript
  function foo() {
    const x = 1;

    // 중첩 함수지만 외부 함수보다 일찍 소멸한다
    function bar() {
      console.log(x);
    }
    bar();
  }

  foo();
  ```
- `bar`는 상위 스코프의 `x`를 참조하지만 **외부 함수 `foo`보다 생명 주기가 짧다**.
  - `foo`가 종료되면 `bar`도 함께 소멸하므로 클로저의 본질에 부합하지 않는다.
- 따라서 **클로저는 중첩 함수가 상위 스코프의 식별자를 참조하고 있고 중첩 함수가 외부 함수보다 더 오래 유지되는 경우**로 한정하는 것이 일반적이다.

#### 자유 변수

- 클로저에 의해 참조되는 상위 스코프의 변수를 **자유 변수(free variable)** 라 한다.
  - 클로저란 "**자유 변수에 묶여있는(close) 함수**"라는 의미다.
  - ```javascript
    function makeCounter() {
      let count = 0; // 자유 변수

      return function () {
        return ++count;
      };
    }
    ```
- 클로저가 **상위 스코프의 모든 식별자를 기억하는 것은 아니다**.
  - 모던 엔진은 **참조하고 있는 식별자만 기억**한다. (최적화)
  - ```javascript
    function foo() {
      const x = 1;
      const y = 2; // 참조되지 않으므로 기억하지 않는다

      return function () {
        console.log(x);
      };
    }
    ```

### 클로저의 활용

- 클로저는 **상태를 안전하게 변경하고 유지하기 위해 사용**한다.
  - 즉 상태를 안전하게 **은닉(information hiding)** 하고 특정 함수에게만 상태 변경을 허용한다.
- 다음은 함수가 호출될 때마다 호출된 횟수를 누적하는 예제다.
  - ```javascript
    // 잘못된 예시 1: 전역 변수 사용
    let num = 0;

    const increase = function () {
      return ++num;
    };

    console.log(increase()); // 1
    console.log(increase()); // 2

    num = 100; // 누구나 변경할 수 있다
    console.log(increase()); // 101
    ```
  - `num`이 전역 변수이므로 **누구나 접근하고 변경할 수 있다**. ([14장](../../week06/윤홍비/14.전역변수의_문제점.md#전역-변수의-문제점))
- 상태를 함수 내부로 옮기면 은닉은 되지만 유지되지 않는다.
  - ```javascript
    // 잘못된 예시 2: 지역 변수 사용
    const increase = function () {
      let num = 0; // 호출될 때마다 초기화된다
      return ++num;
    };

    console.log(increase()); // 1
    console.log(increase()); // 1 (유지되지 않는다)
    ```
- **클로저를 사용하면 두 가지를 모두 해결할 수 있다**.
  - ```javascript
    const increase = (function () {
      let num = 0; // 은닉된 상태

      // 클로저를 반환한다
      return function () {
        return ++num;
      };
    })();

    console.log(increase()); // 1
    console.log(increase()); // 2
    console.log(increase()); // 3

    console.log(num); // ReferenceError: num is not defined
    ```
  - 즉시 실행 함수는 한 번만 실행되므로 `num`이 초기화되지 않는다. ([12장](../../week05/윤홍비/12.함수.md#즉시-실행-함수))
  - `num`은 외부에서 접근할 수 없으므로 **의도되지 않은 변경을 걱정할 필요가 없다**.
- 카운터를 증가/감소시킬 수 있도록 확장하면 다음과 같다.
  - ```javascript
    const counter = (function () {
      let num = 0; // 자유 변수

      // 두 클로저가 같은 렉시컬 환경을 공유한다
      return {
        increase() {
          return ++num;
        },
        decrease() {
          return num > 0 ? --num : 0;
        },
      };
    })();

    console.log(counter.increase()); // 1
    console.log(counter.increase()); // 2
    console.log(counter.decrease()); // 1
    console.log(counter.decrease()); // 0
    ```
  - 중요한 점은 **두 메서드가 같은 렉시컬 환경을 공유**한다는 것이다.

    ```mermaid
    flowchart RL
        INC["increase<br/>[[Environment]]"]
        DEC["decrease<br/>[[Environment]]"]
        IIFE["즉시 실행 함수의 렉시컬 환경<br/>num: 0"]

        INC ==> IIFE
        DEC ==> IIFE
    ```

    같은 환경을 가리키므로 하나의 `num`을 공유한다.

- 생성자 함수로 표현하면 다음과 같다.
  - ```javascript
    const Counter = (function () {
      let num = 0; // 프로토타입 메서드도 접근할 수 있다

      function Counter() {}

      Counter.prototype.increase = function () {
        return ++num;
      };

      Counter.prototype.decrease = function () {
        return num > 0 ? --num : 0;
      };

      return Counter;
    })();

    const counter = new Counter();

    console.log(counter.increase()); // 1
    console.log(counter.decrease()); // 0
    console.log(counter.num); // undefined (은닉되었다)
    ```
  - `num`은 인스턴스의 프로퍼티가 아니므로 **외부에서 접근할 수 없다**. ([19장](../../week07/윤홍비/19.프로토타입.md#프로토타입-체인))
  - 다만 **모든 인스턴스가 하나의 `num`을 공유**하므로 주의가 필요하다.
- 함수형 프로그래밍에서는 **부수 효과를 최대한 억제하기 위해** 클로저를 적극 활용한다. ([12장](../../week05/윤홍비/12.함수.md#순수-함수와-비순수-함수))
  - ```javascript
    // 고차 함수로 상태를 유지한다
    function makeCounter(predicate) {
      let counter = 0; // 자유 변수 (makeCounter마다 독립적이다)

      return function () {
        counter = predicate(counter);
        return counter;
      };
    }

    function increase(n) {
      return ++n;
    }
    function decrease(n) {
      return --n;
    }

    // 함수를 호출할 때마다 새로운 렉시컬 환경이 생성된다
    const increaser = makeCounter(increase);
    console.log(increaser()); // 1
    console.log(increaser()); // 2

    const decreaser = makeCounter(decrease);
    console.log(decreaser()); // -1 (0에서 시작한다)
    console.log(decreaser()); // -2
    ```
  - **함수를 호출할 때마다 독립적인 렉시컬 환경이 생성**되므로 `counter`를 공유하지 않는다.
  - 하나의 `counter`를 공유하려면 **렉시컬 환경을 공유하는 클로저를 만들어야 한다**.
  - ```javascript
    const counter = (function () {
      let counter = 0; // 하나의 자유 변수를 공유한다

      return function (predicate) {
        counter = predicate(counter);
        return counter;
      };
    })();

    console.log(counter(increase)); // 1
    console.log(counter(increase)); // 2
    console.log(counter(decrease)); // 1
    ```

#### 실제 라이브러리에서의 클로저 — Zustand

- 상태 관리 라이브러리 **Zustand**는 위에서 본 패턴을 그대로 사용한다.
  - 스토어를 만드는 `createStore`의 핵심은 다음과 같다. (타입 표기를 덜어낸 형태다)
  - ```javascript
    const createStoreImpl = (createState) => {
      let state; // 자유 변수 (은닉된 상태)
      const listeners = new Set(); // 자유 변수 (구독자 목록)

      const setState = (partial, replace) => {
        const nextState =
          typeof partial === "function" ? partial(state) : partial;

        if (!Object.is(nextState, state)) {
          const previousState = state;
          state =
            replace ?? (typeof nextState !== "object" || nextState === null)
              ? nextState
              : Object.assign({}, state, nextState);

          listeners.forEach((listener) => listener(state, previousState));
        }
      };

      const getState = () => state;
      const getInitialState = () => initialState;

      const subscribe = (listener) => {
        listeners.add(listener);
        return () => listeners.delete(listener); // 해제 함수도 클로저다
      };

      // 네 함수가 같은 렉시컬 환경을 공유한다
      const api = { setState, getState, getInitialState, subscribe };
      const initialState = (state = createState(setState, getState, api));
      return api;
    };
    ```

- 구조를 뜯어보면 앞서 만든 `counter` 객체와 동일하다.
  - `state`와 `listeners`는 `createStoreImpl`의 **지역 변수**이므로 외부에서 접근할 수 없다.
  - 반환하는 `api` 객체의 메서드들이 **같은 렉시컬 환경을 공유**하는 클로저다.

    ```mermaid
    flowchart RL
        SET["setState"]
        GET["getState"]
        SUB["subscribe"]
        ENV["createStoreImpl의 렉시컬 환경<br/>state (은닉)<br/>listeners (은닉)"]

        SET ==> ENV
        GET ==> ENV
        SUB ==> ENV
    ```

- 따라서 **상태를 바꿀 수 있는 유일한 통로가 `setState`로 제한된다**.
  - ```javascript
    import { createStore } from "zustand/vanilla";

    const store = createStore((set) => ({
      count: 0,
      increase: () => set((s) => ({ count: s.count + 1 })),
    }));

    console.log(Object.keys(store));
    // ['setState', 'getState', 'getInitialState', 'subscribe']

    console.log(store.state); // undefined (state는 은닉되어 있다)

    store.getState().increase();
    store.getState().increase();
    console.log(store.getState().count); // 2
    ```
  - 반환된 객체에는 `state`가 **아예 없다**.
    - 전역 변수로 상태를 두었다면 누구나 덮어쓸 수 있었을 것이다. ([14장](../../week06/윤홍비/14.전역변수의_문제점.md#전역-변수의-문제점))
    - 클로저로 가둠으로써 **의도된 방법으로만 상태를 변경**하게 만든다.
- 스토어를 여러 개 만들면 **각각 독립적인 렉시컬 환경**을 갖는다.
  - ```javascript
    const other = createStore(() => ({ count: 100 }));

    console.log(store.getState().count); // 2
    console.log(other.getState().count); // 100 (서로 영향이 없다)
    ```
  - 앞의 `makeCounter(increase)`와 `makeCounter(decrease)`가 `counter`를 공유하지 않던 것과 같은 원리다.
- `subscribe`가 반환하는 **해제 함수도 클로저**다.
  - 자신이 등록한 `listener`를 기억하고 있다가 `listeners`에서 제거한다.
  - ```javascript
    const unsub = store.subscribe((s) => console.log("알림:", s.count));

    store.getState().increase(); // 알림: 3
    unsub(); // 등록했던 listener를 기억하고 있다가 제거한다
    store.getState().increase(); // (알림이 오지 않는다)
    ```
  - 다만 **해제하지 않으면 `listeners`가 `listener`를 계속 참조**하므로 메모리에 남는다.
    - 클로저가 상위 스코프를 붙잡고 있는 한 가비지 컬렉션의 대상이 되지 않기 때문이다.
    - React에서 `useEffect`의 정리 함수로 구독을 해제해야 하는 이유가 이것이다.

### 캡슐화와 정보 은닉

- **캡슐화(encapsulation)** 는 객체의 상태를 나타내는 프로퍼티와 메서드를 하나로 묶는 것이다.
  - 특정 프로퍼티나 메서드를 감출 목적으로 사용하기도 하는데 이를 **정보 은닉**이라 한다.
- 많은 객체지향 언어는 `public`, `private`, `protected` 같은 **접근 제한자**를 제공한다.
  - 하지만 자바스크립트는 접근 제한자를 제공하지 않는다. (ES2022 이전)
  - 따라서 객체의 모든 프로퍼티와 메서드는 기본적으로 외부에 공개된다.
- ```javascript
  function Person(name, age) {
    this.name = name; // public
    let _age = age; // private (지역 변수)

    // 인스턴스 메서드 (클로저)
    this.sayHi = function () {
      console.log(`Hi! My name is ${this.name}. I am ${_age}.`);
    };
  }

  const me = new Person("Lee", 20);
  me.sayHi(); // Hi! My name is Lee. I am 20.
  console.log(me.name); // Lee
  console.log(me._age); // undefined (은닉되었다)
  ```
  - `_age`는 생성자 함수의 지역 변수이므로 외부에서 접근할 수 없다.
  - `sayHi`는 클로저이므로 `_age`를 참조할 수 있다.
- 다만 `sayHi`를 **인스턴스 메서드로 정의하면 중복 생성**되는 문제가 있다. ([19장](../../week07/윤홍비/19.프로토타입.md#상속과-프로토타입))
  - 프로토타입 메서드로 변경하면 중복은 해결되지만 **`_age`를 참조할 수 없게 된다**.
  - ```javascript
    function Person(name, age) {
      this.name = name;
      let _age = age;
    }

    Person.prototype.sayHi = function () {
      // _age를 참조할 수 없다 (상위 스코프가 전역이다)
      console.log(`Hi! My name is ${this.name}. I am ${_age}.`); // ReferenceError
    };
    ```
- 즉시 실행 함수로 감싸면 프로토타입 메서드에서도 참조할 수 있다.
  - ```javascript
    const Person = (function () {
      let _age = 0; // private

      function Person(name, age) {
        this.name = name;
        _age = age;
      }

      Person.prototype.sayHi = function () {
        console.log(`Hi! My name is ${this.name}. I am ${_age}.`);
      };

      return Person;
    })();

    const me = new Person("Lee", 20);
    me.sayHi(); // Hi! My name is Lee. I am 20.

    const you = new Person("Kim", 30);
    you.sayHi(); // Hi! My name is Kim. I am 30.

    me.sayHi(); // Hi! My name is Lee. I am 30. (_age가 덮어써졌다)
    ```
  - 하지만 **프로토타입 메서드가 하나의 `_age`를 공유**하므로 인스턴스가 여러 개면 상태가 섞인다.

    ```mermaid
    flowchart TB
        AGE["_age (하나뿐이다)"]
        SAYHI["Person.prototype.sayHi"]

        ME["me 생성 → _age = 20"]
        YOU["you 생성 → _age = 30 (덮어쓴다)"]
        CALL["me.sayHi() → 30 출력"]

        SAYHI ==>|참조| AGE
        ME ==> YOU ==> CALL
    ```

- 결론적으로 **자바스크립트는 클로저만으로 완전한 정보 은닉을 구현하기 어렵다**.
  - ES2022부터 **클래스의 private 필드(`#`)** 가 도입되어 이 문제가 해결되었다.
  - ```javascript
    class Person {
      #age; // private 필드

      constructor(name, age) {
        this.name = name;
        this.#age = age;
      }

      sayHi() {
        console.log(`Hi! My name is ${this.name}. I am ${this.#age}.`);
      }
    }

    const me = new Person("Lee", 20);
    const you = new Person("Kim", 30);

    me.sayHi(); // Hi! My name is Lee. I am 20. (인스턴스별로 독립적이다)
    you.sayHi(); // Hi! My name is Kim. I am 30.
    // console.log(me.#age); // SyntaxError
    ```

### 자주 발생하는 실수

#### 반복문과 클로저

- 다음 코드는 `0`, `1`, `2`를 출력할 것처럼 보이지만 `3`을 세 번 출력한다.
  - ```javascript
    var funcs = [];

    for (var i = 0; i < 3; i++) {
      funcs[i] = function () {
        return i;
      };
    }

    for (var j = 0; j < funcs.length; j++) {
      console.log(funcs[j]()); // 3 3 3
    }
    ```
  - `var`는 **함수 레벨 스코프**이므로 `i`는 전역 변수다. ([15장](../../week06/윤홍비/15.let,const키워드와_블록레벨스코프.md#함수-레벨-스코프))
  - 세 함수가 모두 **같은 전역 변수 `i` 하나를 참조**하고 있다.
  - 반복이 끝난 시점의 `i`는 `3`이므로 모두 `3`을 반환한다.

    ```mermaid
    flowchart RL
        F0["funcs[0].[[Environment]]"]
        F1["funcs[1].[[Environment]]"]
        F2["funcs[2].[[Environment]]"]
        GLE["전역 렉시컬 환경<br/>i: 3"]

        F0 ==> GLE
        F1 ==> GLE
        F2 ==> GLE
    ```

    하나의 `i`를 공유하므로 모두 `3`을 반환한다.


##### 해결 1. 즉시 실행 함수 (ES5)

- ```javascript
  var funcs = [];

  for (var i = 0; i < 3; i++) {
    funcs[i] = (function (id) {
      // id는 즉시 실행 함수의 매개변수다
      return function () {
        return id;
      };
    })(i); // 현재 i 값을 인수로 전달한다
  }

  for (var j = 0; j < funcs.length; j++) {
    console.log(funcs[j]()); // 0 1 2
  }
  ```
  - 반복마다 즉시 실행 함수가 호출되어 **독립적인 렉시컬 환경이 생성**된다.
  - 각 함수는 자신만의 `id`를 기억한다.

##### 해결 2. let 키워드 (ES6)

- ```javascript
  const funcs = [];

  for (let i = 0; i < 3; i++) {
    funcs[i] = function () {
      return i;
    };
  }

  for (let j = 0; j < funcs.length; j++) {
    console.log(funcs[j]()); // 0 1 2
  }
  ```
  - `let`은 **블록 레벨 스코프**이므로 반복마다 새로운 렉시컬 환경이 생성된다. ([23장](./23.실행컨텍스트.md#실행-컨텍스트와-블록-레벨-스코프))

    ```mermaid
    flowchart RL
        F0["funcs[0].[[Environment]]"]
        F1["funcs[1].[[Environment]]"]
        F2["funcs[2].[[Environment]]"]

        B0["1회차 블록 렉시컬 환경<br/>i: 0"]
        B1["2회차 블록 렉시컬 환경<br/>i: 1"]
        B2["3회차 블록 렉시컬 환경<br/>i: 2"]

        F0 ==> B0
        F1 ==> B1
        F2 ==> B2
    ```

    각각 독립적인 `i`를 기억하므로 `0`, `1`, `2`를 반환한다.

  - 반복할 때마다 **이전 반복의 렉시컬 환경을 상위 스코프로 하는 새로운 환경이 생성**된다.
- 사실 함수형 프로그래밍 기법을 사용하면 변수와 반복문 자체를 제거할 수도 있다.
  - ```javascript
    const funcs = [0, 1, 2].map((i) => () => i);

    funcs.forEach((f) => console.log(f())); // 0 1 2
    ```

#### setTimeout과 클로저

- 같은 원인으로 `setTimeout`에서도 자주 발생한다.
  - ```javascript
    for (var i = 1; i <= 3; i++) {
      setTimeout(() => console.log(i), i * 1000); // 4 4 4
    }

    for (let i = 1; i <= 3; i++) {
      setTimeout(() => console.log(i), i * 1000); // 1 2 3
    }
    ```
  - 콜백이 실행되는 시점에는 이미 반복이 끝났으므로 `var`는 최종 값을 참조한다.

### 정리

| 개념                  | 설명                                                        |
| --------------------- | ----------------------------------------------------------- |
| 클로저                | 함수와 그 함수가 선언된 **렉시컬 환경의 조합**              |
| `[[Environment]]`     | 함수 객체가 **정의 시점의 상위 스코프**를 저장하는 내부 슬롯 |
| 자유 변수             | 클로저가 참조하는 **상위 스코프의 변수**                    |
| 클로저가 유지되는 이유 | 렉시컬 환경이 **참조되고 있어 GC 대상이 아니기 때문**        |

- 클로저가 가능한 이유는 두 가지 메커니즘 때문이다.
  - 함수 객체는 `[[Environment]]`에 **정의 시점의 렉시컬 환경을 저장**한다. (렉시컬 스코프)
  - 실행 컨텍스트가 제거되어도 **참조되는 렉시컬 환경은 소멸하지 않는다**. ([23장](./23.실행컨텍스트.md#810-함수-코드-실행-종료))
- 클로저는 **상태를 은닉하고 유지**하기 위해 사용한다.
  - 전역 변수를 사용하지 않고도 상태를 지속시킬 수 있다.
  - 같은 렉시컬 환경을 공유하면 **상태를 공유**하고, 함수를 다시 호출하면 **독립적인 상태**를 갖는다.
- 주의할 점은 **무엇을 기억하고 있는지 정확히 파악해야 한다**는 것이다.
  - `var`는 함수 레벨 스코프이므로 반복문에서 **하나의 변수를 공유**한다.
  - `let`, `const`는 블록 레벨 스코프이므로 **반복마다 독립적인 환경**이 생성된다.
- 다음 장에서 다루는 클래스의 private 필드는 클로저로 구현했던 정보 은닉을 **언어 차원에서 지원**한다. (25장)
