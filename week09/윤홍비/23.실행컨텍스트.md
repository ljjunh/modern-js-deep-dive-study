### 소스코드의 타입

- ECMAScript 사양은 소스코드를 4가지 타입으로 구분한다.
  - **4가지 타입의 소스코드는 실행 컨텍스트를 생성한다**.
  - 타입에 따라 실행 컨텍스트를 생성하는 과정과 관리 내용이 다르기 때문이다.

| 소스코드 타입     | 설명                                       | 실행 컨텍스트            |
| ----------------- | ------------------------------------------ | ------------------------ |
| 전역 코드         | 전역에 존재하는 소스코드 (함수, 클래스 제외) | 전역 실행 컨텍스트       |
| 함수 코드         | 함수 내부에 존재하는 소스코드              | 함수 실행 컨텍스트       |
| eval 코드         | `eval` 함수에 인수로 전달된 소스코드       | strict mode 실행 컨텍스트 |
| 모듈 코드         | 모듈 내부에 존재하는 소스코드              | 모듈 실행 컨텍스트       |

- **전역 코드**는 전역 변수를 관리하기 위해 최상위 스코프인 전역 스코프를 생성해야 한다.
  - 또한 `var` 키워드로 선언된 전역 변수와 함수 선언문으로 정의된 전역 함수를 **전역 객체의 프로퍼티와 메서드로 바인딩**하고 참조하기 위해 전역 객체와 연결되어야 한다.
  - 이를 위해 전역 코드가 평가되면 전역 실행 컨텍스트가 생성된다.
- **함수 코드**는 지역 스코프를 생성하고 지역 변수, 매개변수, arguments 객체를 관리해야 한다.
  - 또한 생성한 지역 스코프를 전역 스코프에서 시작하는 **스코프 체인의 일원으로 연결**해야 한다.
  - 이를 위해 함수 코드가 평가되면 함수 실행 컨텍스트가 생성된다.
- **eval 코드**는 strict mode에서 자신만의 독자적인 스코프를 생성한다.
- **모듈 코드**는 모듈별로 독립적인 모듈 스코프를 생성한다. ([14장](../../week06/윤홍비/14.전역변수의_문제점.md#es6-모듈))

### 소스코드의 평가와 실행

- 자바스크립트 엔진은 소스코드를 **평가**와 **실행** 2개의 과정으로 나누어 처리한다.
  - **평가** 과정에서는 실행 컨텍스트를 생성하고 변수, 함수 등의 선언문만 먼저 실행하여 **스코프에 등록**한다.
  - **실행** 과정에서는 선언문을 제외한 소스코드가 순차적으로 실행된다.
    - 이때 필요한 정보, 즉 변수나 함수의 참조를 실행 컨텍스트가 관리하는 스코프에서 검색해서 취득한다.
    - 변수 값의 변경 등 실행 결과는 다시 실행 컨텍스트가 관리하는 스코프에 등록된다.
- 예를 들어 다음 코드를 보면 평가와 실행이 어떻게 나뉘는지 알 수 있다.
  - ```javascript
    var x;
    x = 1;
    ```
  - **평가 시점**: `var x;` 선언문이 실행되어 x가 스코프(변수 객체)에 등록되고 undefined로 초기화된다.
  - **실행 시점**: `x = 1;` 할당문이 실행된다.
    - 먼저 x가 스코프에 등록되어 있는지 확인한다. (선언된 변수인지 확인)
    - 등록되어 있다면 값 1을 할당하고 그 결과를 다시 스코프에 등록해 관리한다.
- 이것이 **변수 호이스팅**이 발생하는 근본적인 원인이다. ([4장](../../week02/윤홍비/04.변수.md#변수-선언과-호이스팅))
  - 선언문은 평가 단계에서 **이미 처리되었기 때문에** 실행 단계에서는 이미 존재하는 변수가 된다.
  - ```javascript
    console.log(x); // undefined (에러가 아니다)
    var x = 1;

    // 엔진이 처리하는 순서
    // 1. 평가: var x → 스코프에 x 등록, undefined로 초기화
    // 2. 실행: console.log(x) → 스코프에서 x를 찾음 → undefined
    // 3. 실행: x = 1 → 값 할당
    ```

### 실행 컨텍스트의 역할

- 다음 예제를 통해 자바스크립트 엔진이 코드를 어떻게 평가하고 실행하는지 살펴보자.
  - ```javascript
    var x = 1;
    const y = 2;

    function foo(a) {
      var x = 3;
      const y = 4;

      function bar(b) {
        const z = 5;
        console.log(a + b + x + y + z);
      }
      bar(10);
    }

    foo(20); // 42
    ```

#### 1. 전역 코드 평가

- 전역 코드를 실행하기 전에 먼저 평가 과정을 거치며 전역 코드를 실행하기 위한 준비를 한다.
  - 소스코드 평가 과정에서는 선언문만 먼저 실행한다.
  - 따라서 전역 코드의 변수 선언문과 함수 선언문이 먼저 실행된다.
  - 그 결과 생성된 전역 변수와 전역 함수가 **전역 스코프에 등록**된다.
- 이때 `var` 키워드로 선언된 전역 변수와 함수 선언문으로 정의된 전역 함수는 **전역 객체의 프로퍼티와 메서드**가 된다. ([14장](../../week06/윤홍비/14.전역변수의_문제점.md#전역-변수의-생명-주기))
  - 반면 `let`, `const`로 선언한 변수는 전역 객체의 프로퍼티가 되지 않는다. ([15장](../../week06/윤홍비/15.let,const키워드와_블록레벨스코프.md#전역-객체와-let))

#### 2. 전역 코드 실행

- 전역 코드 평가가 끝나면 런타임이 시작되어 전역 코드가 순차적으로 실행된다.
  - 전역 변수에 값이 할당되고 함수가 호출된다.
  - 이때 변수나 함수의 참조는 **스코프 체인에서 검색**해서 취득한다. ([13장](../../week05/윤홍비/13.스코프.md#스코프-체인))

#### 3. foo 함수 코드 평가

- `foo` 함수가 호출되면 전역 코드의 실행을 일시 중단하고 **foo 함수 내부로 코드의 제어권이 이동**한다.
  - 그리고 함수 코드 평가가 시작된다.
  - 이때 매개변수와 지역 변수 선언문이 먼저 실행되고 **함수 지역 스코프에 등록**된다.
  - 또한 함수 내부에서 사용할 `arguments` 객체와 `this` 바인딩도 결정된다. ([22장](../../week08/윤홍비/22.this.md#this-키워드))

#### 4. foo 함수 코드 실행

- 평가가 끝나면 런타임이 시작되어 함수 몸체의 코드가 순차적으로 실행된다.
  - 이때 식별자는 **스코프 체인을 따라 검색**한다.
  - 자신의 스코프에서 찾지 못하면 상위 스코프로 이동해 검색한다.

#### 5~6. bar 함수 코드 평가와 실행

- `bar` 함수가 호출되면 동일한 과정이 반복된다.
  - `console.log(a + b + x + y + z)`가 실행되면서 각 식별자를 스코프 체인에서 검색한다.
  - `z`는 bar의 지역 스코프에서, `b`는 bar의 매개변수에서 찾는다.
  - `x`, `y`, `a`는 **상위 스코프인 foo의 스코프**에서 찾는다.

    ```mermaid
    flowchart TB
        BAR["bar 스코프<br/>z = 5, b = 10"]
        FOO["foo 스코프<br/>x = 3, y = 4, a = 20"]
        GLOBAL["전역 스코프<br/>x = 1, y = 2, foo"]
        RESULT["20 + 10 + 3 + 4 + 5 = 42"]

        BAR -.->|"x, y, a 없음 → 상위로"| FOO
        FOO -.->|"console 없음 → 상위로"| GLOBAL
        BAR ==> RESULT
    ```

  - 전역 변수 `x = 1`, `y = 2`가 아닌 **foo의 지역 변수 3, 4가 사용**된다.

- 이처럼 **코드가 실행되려면 다음과 같은 정보를 관리해야 한다**.
  - 선언에 의해 생성된 모든 식별자를 스코프를 구분해서 등록하고 상태 변화를 지속적으로 관리해야 한다.
  - 스코프는 중첩에 의해 **스코프 체인**을 형성해야 하며, 상위 스코프로 이동하며 식별자를 검색할 수 있어야 한다.
  - 현재 실행 중인 코드의 실행 순서를 변경(함수 호출에 의한 실행 순서 변경)할 수 있어야 하며 다시 되돌아갈 수도 있어야 한다.
- **이 모든 것을 관리하는 것이 바로 실행 컨텍스트다**.
  - 실행 컨텍스트는 소스코드를 **실행하는 데 필요한 환경을 제공하고 코드의 실행 결과를 실제로 관리하는 영역**이다.
  - 식별자와 스코프는 실행 컨텍스트의 **렉시컬 환경**으로 관리한다.
  - 코드 실행 순서는 **실행 컨텍스트 스택**으로 관리한다.

### 실행 컨텍스트 스택

- 실행 컨텍스트는 **스택(stack) 자료구조로 관리**된다.
  - 이를 **실행 컨텍스트 스택** 또는 콜 스택(call stack)이라 한다.
- 다음 예제를 통해 스택이 어떻게 변하는지 살펴보자.
  - ```javascript
    const x = 1;

    function foo() {
      const y = 2;

      function bar() {
        const z = 3;
        console.log(x + y + z);
      }
      bar();
    }

    foo(); // 6
    ```
- 코드가 실행되면 실행 컨텍스트 스택은 다음과 같이 변화한다.

    ```mermaid
    flowchart LR
        subgraph S1["① 전역 코드 평가/실행"]
            direction TB
            A1["전역"]
        end

        subgraph S2["② foo 호출"]
            direction TB
            B2["foo"] --- B1["전역"]
        end

        subgraph S3["③ bar 호출"]
            direction TB
            C3["bar"] --- C2["foo"] --- C1["전역"]
        end

        subgraph S4["④ bar 종료"]
            direction TB
            D2["foo"] --- D1["전역"]
        end

        subgraph S5["⑤ foo 종료"]
            direction TB
            E1["전역"]
        end

        subgraph S6["⑥ 전역 종료"]
            direction TB
            F1["(비어짐)"]
        end

        S1 ==>|"push (foo 호출)"| S2 ==>|"push (bar 호출)"| S3
        S3 ==>|"pop (bar 반환)"| S4 ==>|"pop (foo 반환)"| S5 ==>|"pop (애플리케이션 종료)"| S6
    ```

  - 스택의 **최상위 요소가 현재 실행 중인 실행 컨텍스트**다.
  - 이를 **실행 중인 실행 컨텍스트(running execution context)** 라 한다.
- 즉 실행 컨텍스트 스택은 **코드의 실행 순서를 관리**한다.
  - 함수가 호출되면 실행 컨텍스트가 **푸시(push)** 되고, 함수가 종료되면 **팝(pop)** 된다.
  - 팝되면 이전 실행 컨텍스트가 다시 실행 중인 실행 컨텍스트가 되어 **중단된 지점부터 재개**된다.
- 전역 실행 컨텍스트는 애플리케이션이 종료될 때(브라우저 탭을 닫거나 페이지를 이동할 때)까지 유지된다.

### 렉시컬 환경

- **렉시컬 환경(Lexical Environment)** 은 식별자와 식별자에 바인딩된 값, 그리고 상위 스코프에 대한 참조를 기록하는 자료구조다.
  - 실행 컨텍스트를 구성하는 컴포넌트다.
  - 실행 컨텍스트 스택이 코드의 실행 순서를 관리한다면, 렉시컬 환경은 **스코프와 식별자를 관리**한다.
- 렉시컬 환경은 키와 값을 갖는 객체 형태의 스코프를 생성하여 식별자를 키로 등록하고 값을 관리한다.
  - 즉 렉시컬 환경은 **스코프를 구분하여 식별자를 등록하고 관리하는 저장소 역할을 하는 렉시컬 스코프의 실체**다.
- 렉시컬 환경은 다음 두 개의 컴포넌트로 구성된다.

    ```mermaid
    flowchart TB
        EC["실행 컨텍스트"]
        LE["LexicalEnvironment<br/>(렉시컬 환경)"]
        ER["EnvironmentRecord<br/>(환경 레코드)"]
        DER["DeclarativeEnvironmentRecord<br/>(선언적 환경 레코드)"]
        OER["ObjectEnvironmentRecord<br/>(객체 환경 레코드)"]
        OUT["OuterLexicalEnvironmentReference<br/>(외부 렉시컬 환경에 대한 참조)"]

        EC --> LE
        LE --> ER
        LE --> OUT
        ER --> DER
        ER --> OER
    ```


#### 1. 환경 레코드 (EnvironmentRecord)

- 스코프에 포함된 **식별자를 등록하고 등록된 식별자에 바인딩된 값을 관리하는 저장소**다.
  - 환경 레코드는 소스코드의 타입에 따라 관리하는 내용에 차이가 있다.
- 전역 환경 레코드는 **객체 환경 레코드**와 **선언적 환경 레코드**로 구성된다.
  - **객체 환경 레코드**는 `var` 키워드로 선언한 전역 변수와 함수 선언문으로 정의한 전역 함수, 빌트인 전역 프로퍼티와 빌트인 전역 함수를 관리한다. ([21장](../../week08/윤홍비/21.빌트인_객체.md))
  - **선언적 환경 레코드**는 `let`, `const` 키워드로 선언한 전역 변수를 관리한다.

    ```mermaid
    flowchart LR
        subgraph GLE["전역 렉시컬 환경"]
            direction TB
            OER["객체 환경 레코드"]
            DER["선언적 환경 레코드<br/>let y, const z<br/>(엔진 내부에 직접 저장)"]
        end

        WIN["전역 객체 (window)<br/>var x, function foo<br/>Object, Array ..."]
        NOBJ["연결된 객체가 없다"]

        OER ==>|"BindingObject (연결)"| WIN
        DER -.->|"BindingObject 없음"| NOBJ
    ```

- **BindingObject는 객체 환경 레코드만 갖는다**.
  - 객체 환경 레코드는 식별자의 등록과 조회를 **BindingObject의 프로퍼티 조작으로 위임**한다.
    - 즉 `var x = 1`은 결국 전역 객체에 `x` 프로퍼티를 만드는 것과 같다.
  - 반면 선언적 환경 레코드는 연결된 객체 없이 **엔진 내부 자료구조에 바인딩을 직접 저장**한다.
    - 따라서 `let`, `const`로 선언한 변수는 **어떤 객체의 프로퍼티도 되지 않는다**.
  - 이것이 바로 `let`과 `const`로 선언한 전역 변수가 **전역 객체의 프로퍼티가 되지 않는 이유**다. ([15장](../../week06/윤홍비/15.let,const키워드와_블록레벨스코프.md#전역-객체와-let))
  - ```javascript
    var x = 1;
    let y = 2;

    console.log(window.x); // 1 (객체 환경 레코드 → 전역 객체)
    console.log(window.y); // undefined (선언적 환경 레코드)
    ```

#### 2. 외부 렉시컬 환경에 대한 참조 (OuterLexicalEnvironmentReference)

- 해당 실행 컨텍스트를 생성한 소스코드를 포함하는 **상위 코드의 렉시컬 환경, 즉 상위 스코프를 가리킨다**.
  - 이를 통해 **단방향 링크드 리스트인 스코프 체인을 구현**한다.

    ```mermaid
    flowchart LR
        BAR["bar의 렉시컬 환경"]
        FOO["foo의 렉시컬 환경"]
        GLOBAL["전역 렉시컬 환경"]
        NULL["null<br/>(스코프 체인의 종점)"]

        BAR ==>|Outer| FOO
        FOO ==>|Outer| GLOBAL
        GLOBAL ==>|Outer| NULL
    ```

  - 식별자를 검색할 때 이 참조를 따라 상위 스코프로 이동한다.
  - 전역 렉시컬 환경의 Outer는 `null`이며 이것이 **스코프 체인의 종점**이다. ([13장](../../week05/윤홍비/13.스코프.md#스코프-체인))
- 중요한 점은 **이 참조가 함수를 정의한 위치에 의해 결정된다**는 것이다.
  - 함수가 호출된 위치가 아니라 **정의된 위치**의 렉시컬 환경을 가리킨다.
  - 이것이 자바스크립트가 **렉시컬 스코프를 따르는 메커니즘**이다. ([13장](../../week05/윤홍비/13.스코프.md#렉시컬-스코프))
  - 반면 `this` 바인딩은 호출 방식에 따라 결정되므로 결정 시기가 다르다. ([22장](../../week08/윤홍비/22.this.md#함수-호출-방식과-this-바인딩))

### 실행 컨텍스트의 생성과 식별자 검색 과정

- 다음 예제가 어떻게 실행되는지 단계별로 살펴보자.
  - ```javascript
    var x = 1;
    const y = 2;

    function foo(a) {
      var x = 3;
      const y = 4;

      function bar(b) {
        const z = 5;
        console.log(a + b + x + y + z);
      }
      bar(10);
    }

    foo(20); // 42
    ```

#### 1. 전역 객체 생성

- 전역 객체는 **전역 코드가 평가되기 이전에 생성**된다.
  - 이때 빌트인 전역 프로퍼티와 빌트인 전역 함수, 표준 빌트인 객체가 추가된다. ([21장](../../week08/윤홍비/21.빌트인_객체.md))
  - 또한 Object.prototype을 상속받으므로 프로토타입 체인의 일원이 된다. ([19장](../../week07/윤홍비/19.프로토타입.md#프로토타입-체인))

#### 2. 전역 코드 평가

- 전역 코드 평가는 다음 순서로 진행된다.
  - 1. 전역 실행 컨텍스트 생성
  - 2. 전역 렉시컬 환경 생성
    - 2.1. 전역 환경 레코드 생성
      - 2.1.1. 객체 환경 레코드 생성
      - 2.1.2. 선언적 환경 레코드 생성
    - 2.2. this 바인딩
    - 2.3. 외부 렉시컬 환경에 대한 참조 결정

##### 2.1.1. 객체 환경 레코드 생성

- 객체 환경 레코드는 **BindingObject라는 객체와 연결**된다.
  - BindingObject는 전역 객체다.
  - 따라서 `var` 변수와 함수 선언문으로 정의된 함수는 전역 객체의 프로퍼티가 된다.

    ```mermaid
    flowchart LR
        OER["객체 환경 레코드"]
        WIN["전역 객체 (window)<br/>x: undefined (var, 호이스팅됨)<br/>foo: function (함수 객체)"]

        OER ==>|BindingObject| WIN
    ```

- 이때 **var 변수는 undefined로 초기화**되지만 함수 선언문으로 정의된 함수는 **함수 객체가 즉시 생성**된다.
  - 이것이 **함수 호이스팅**이다. ([12장](../../week05/윤홍비/12.함수.md#함수-생성-시점과-함수-호이스팅))
  - ```javascript
    console.log(x); // undefined (변수 호이스팅: 선언만 되고 할당은 안 됨)
    foo(); // 정상 호출 (함수 호이스팅: 함수 객체가 이미 생성됨)

    var x = 1;
    function foo() {}
    ```

##### 2.1.2. 선언적 환경 레코드 생성

- `let`, `const`로 선언한 변수는 선언적 환경 레코드에 등록된다.
  - 다만 **초기화 단계가 분리되어 있어 선언문에 도달하기 전까지는 참조할 수 없다**.
  - 이 구간이 **일시적 사각지대(TDZ)** 다. ([15장](../../week06/윤홍비/15.let,const키워드와_블록레벨스코프.md#변수-호이스팅))
  - ```javascript
    console.log(x); // undefined (var: 선언 + 초기화가 한번에)
    console.log(y); // ReferenceError: Cannot access 'y' before initialization

    var x = 1;
    const y = 2;
    ```
  - 즉 `let`, `const`도 **호이스팅은 되지만** 초기화 전에는 접근할 수 없다.
    - 환경 레코드에는 등록되어 있으므로 상위 스코프의 변수를 찾지 않고 에러가 발생한다.

##### 2.2. this 바인딩

- 전역 환경 레코드의 `[[GlobalThisValue]]` 내부 슬롯에 this가 바인딩된다.
  - 전역 코드에서 this는 **전역 객체를 가리킨다**.
  - 선언적 환경 레코드에는 this 바인딩이 없다. (함수 환경 레코드에서만 사용)

##### 2.3. 외부 렉시컬 환경에 대한 참조 결정

- 전역 코드를 포함하는 상위 스코프는 없으므로 **null이 할당**된다.
  - 즉 전역 렉시컬 환경이 스코프 체인의 종점이다.

#### 3. 전역 코드 실행

- 평가가 끝나면 전역 코드가 순차적으로 실행된다.
  - `x = 1`, `y = 2` 할당이 실행되고 `foo(20)`이 호출된다.
  - 이때 식별자는 스코프 체인에서 검색한다.
  - **선언되지 않은 식별자를 참조하면 ReferenceError가 발생한다**.
    - 단 할당의 경우 non-strict mode에서는 암묵적 전역이 발생한다. ([20장](../../week08/윤홍비/20.strict_mode.md#암묵적-전역))

#### 4. foo 함수 코드 평가

- 함수를 호출하면 **함수 내부로 코드의 제어권이 이동**하여 함수 코드를 평가한다.
  - 1. 함수 실행 컨텍스트 생성
  - 2. 함수 렉시컬 환경 생성
    - 2.1. 함수 환경 레코드 생성
    - 2.2. this 바인딩
    - 2.3. 외부 렉시컬 환경에 대한 참조 결정
- **함수 환경 레코드**는 매개변수, arguments 객체, 함수 내부의 지역 변수와 중첩 함수를 등록하고 관리한다. ([18장](../../week05/윤홍비/18.함수와_일급_객체.md#arguments-프로퍼티))

    ```mermaid
    flowchart LR
        subgraph FLE["foo 함수 렉시컬 환경"]
            direction TB
            REC["함수 환경 레코드<br/>arguments: { 0: 20, length: 1 }<br/>a: 20 (매개변수)<br/>x: undefined (var, 호이스팅)<br/>y: uninitialized (const, TDZ)<br/>bar: function (함수 선언문)"]
            THIS["this: 전역 객체<br/>(일반 함수로 호출되었으므로)"]
            OUT["외부 렉시컬 환경에 대한 참조"]
        end

        GLE["전역 렉시컬 환경"]

        OUT ==>|"Outer (foo가 전역에서 정의되었으므로)"| GLE
    ```

- **this 바인딩은 함수 호출 방식에 의해 결정된다**. ([22장](../../week08/윤홍비/22.this.md#함수-호출-방식과-this-바인딩))
  - `foo(20)`은 일반 함수로 호출되었으므로 this에 전역 객체가 바인딩된다.
  - strict mode라면 undefined가 바인딩된다. ([20장](../../week08/윤홍비/20.strict_mode.md#일반-함수의-this))
- **외부 렉시컬 환경에 대한 참조는 foo 함수가 정의된 위치**로 결정된다.
  - foo는 전역에서 정의되었으므로 전역 렉시컬 환경을 가리킨다.
  - 여기서 중요한 것은 **함수 객체를 생성할 때 이미 상위 스코프를 저장해둔다**는 점이다.
    - 함수 객체의 내부 슬롯 `[[Environment]]`에 자신이 정의된 환경을 저장한다.
    - 호출 시점에 이 값을 그대로 Outer에 할당한다.

    ```mermaid
    flowchart LR
        subgraph S1["① 함수 정의 시점 (저장)"]
            direction TB
            A["foo 함수 객체<br/>[[Environment]] = 전역 렉시컬 환경"]
        end

        subgraph S2["② 함수 호출 시점 (복원)"]
            direction TB
            B["foo 렉시컬 환경<br/>Outer = foo.[[Environment]]"]
        end

        S1 ==>|"그대로 할당된다"| S2
    ```

  - 따라서 **어디서 호출되든 상위 스코프는 항상 동일하다**.
    - 이것이 렉시컬 스코프이며, 다음 장에서 다루는 **클로저의 핵심 메커니즘**이다. ([24장](./24.클로저.md#렉시컬-환경과-클로저))

#### 5. foo 함수 코드 실행

- `x = 3`, `y = 4` 할당이 실행되고 `bar(10)`이 호출된다.
  - 이때 `x`는 foo의 함수 환경 레코드에서 찾으므로 **전역 변수 x = 1은 영향을 받지 않는다**.

#### 6~7. bar 함수 코드 평가와 실행

- bar 함수 실행 컨텍스트가 생성되고 동일한 과정이 반복된다.
  - bar의 Outer는 bar가 정의된 위치인 **foo의 렉시컬 환경**을 가리킨다.
- `console.log(a + b + x + y + z)`가 실행되면서 식별자를 검색한다.

    ```mermaid
    flowchart TB
        BAR["bar 환경 레코드<br/>z = 5, b = 10 (매개변수)"]
        FOO["foo 환경 레코드<br/>x = 3, y = 4, a = 20 (매개변수)"]
        GLE["전역 렉시컬 환경<br/>console, x = 1, y = 2, foo"]
        RESULT["20 + 10 + 3 + 4 + 5 = 42"]

        BAR -->|"z, b 즉시 발견"| RESULT
        BAR -.->|"x, y, a 없음 → Outer"| FOO
        FOO -->|"x, y, a 발견"| RESULT
        FOO -.->|"console 없음 → Outer"| GLE
        GLE -->|"console 발견"| RESULT
    ```

  - 이처럼 **식별자 결정(identifier resolution)** 은 실행 중인 실행 컨텍스트의 렉시컬 환경에서 시작해 Outer를 따라 상위 스코프로 이동하며 검색한다.

#### 8~10. 함수 코드 실행 종료

- `console.log`가 종료되면 더 이상 실행할 코드가 없으므로 bar 함수 코드 실행이 종료된다.
  - 실행 컨텍스트 스택에서 bar 실행 컨텍스트가 **팝되어 제거**되고 foo 실행 컨텍스트가 실행 중인 실행 컨텍스트가 된다.
  - 이어서 foo도 종료되고 마지막으로 전역 실행 컨텍스트도 제거된다.
- 주의할 점은 **실행 컨텍스트가 제거되었다고 렉시컬 환경까지 즉시 소멸하는 것은 아니라는 것**이다.
  - 렉시컬 환경은 독립적인 객체이므로 **누군가 참조하고 있다면 메모리에 남는다**.
  - 이것이 클로저가 동작하는 원리다. ([24장](./24.클로저.md#렉시컬-환경과-클로저))

### 실행 컨텍스트와 블록 레벨 스코프

- `var` 키워드로 선언한 변수는 **함수 레벨 스코프**를 따른다. ([15장](../../week06/윤홍비/15.let,const키워드와_블록레벨스코프.md#함수-레벨-스코프))
  - 반면 `let`, `const`로 선언한 변수는 **블록 레벨 스코프**를 따른다.
- 블록 레벨 스코프를 지원하기 위해 **코드 블록이 실행될 때마다 새로운 렉시컬 환경을 생성**한다.
  - ```javascript
    let x = 1;

    if (true) {
      let x = 10; // 새로운 렉시컬 환경이 생성된다
      console.log(x); // 10
    }

    console.log(x); // 1
    ```

    ```mermaid
    flowchart LR
        subgraph BLK["if 블록 렉시컬 환경 (블록 실행 중)"]
            direction TB
            BREC["선언적 환경 레코드<br/>x = 10"]
            BOUT["외부 렉시컬 환경에 대한 참조"]
        end

        GLE["전역 렉시컬 환경<br/>x = 1"]

        BOUT ==>|Outer| GLE
        BLK -.->|"블록 종료 → 교체되어 원래대로 복귀"| GLE
    ```

  - 블록이 실행되면 블록의 렉시컬 환경이 **일시적으로 실행 중인 실행 컨텍스트의 렉시컬 환경을 교체**하고
  - 블록이 종료되면 **원래의 렉시컬 환경으로 복귀**한다.
- `for` 문의 코드 블록도 마찬가지다.
  - 반복할 때마다 **독립적인 렉시컬 환경을 생성**한다.
  - ```javascript
    for (let i = 0; i < 3; i++) {
      setTimeout(() => console.log(i), 0); // 0, 1, 2
    }

    for (var i = 0; i < 3; i++) {
      setTimeout(() => console.log(i), 0); // 3, 3, 3
    }
    ```
  - `let`은 반복마다 새로운 렉시컬 환경이 생성되어 각각 다른 `i`를 기억한다.
  - `var`는 함수 레벨 스코프이므로 **하나의 `i`를 공유**한다.
  - 이것도 클로저와 밀접하게 연관된다. ([24장](./24.클로저.md#반복문과-클로저))

### 정리

| 구성 요소              | 관리 대상                                     |
| ---------------------- | --------------------------------------------- |
| 실행 컨텍스트 스택     | 코드의 **실행 순서** (함수 호출/종료)         |
| 렉시컬 환경            | **스코프와 식별자** (선언, 값, 상위 스코프)   |
| 환경 레코드            | 해당 스코프의 식별자와 바인딩된 값            |
| 외부 렉시컬 환경 참조  | 상위 스코프 (= 스코프 체인)                   |

- 실행 컨텍스트는 소스코드 타입에 따라 생성되며 **스택으로 관리**된다.
  - 함수 호출 시 푸시, 종료 시 팝된다.
  - 최상위 요소가 **실행 중인 실행 컨텍스트**다.
- 렉시컬 환경은 **식별자를 등록하고 상위 스코프를 연결**한다.
  - `var`는 객체 환경 레코드(= 전역 객체)에, `let`/`const`는 선언적 환경 레코드에 등록된다.
  - 외부 렉시컬 환경 참조는 **함수를 정의한 위치**로 결정된다. (렉시컬 스코프)
- 이 장에서 다룬 개념들로 지금까지 배운 내용들이 설명된다.
  - **호이스팅** → 평가 단계에서 선언문이 먼저 처리되기 때문
