- 클로저는 자바스크립트 고유의 개념이 아님. 함수를 일급 객체로 다루는 함수형 언어에 공통으로 있는 특성
- 그래서 ECMAScript 사양에는 클로저의 정의가 없음
- MDN 정의: "클로저는 함수와 그 함수가 선언된 렉시컬 환경의 조합이다"

### 렉시컬 스코프

- 자바스크립트 엔진은 함수를 어디서 호출했는지가 아니라 어디에 정의했는지에 따라 상위 스코프를 정한다. 이것을 렉시컬 스코프(정적 스코프)라고 한다
- 함수의 상위 스코프는 정의한 위치로 정해지고, 이후에 바뀌지 않는다. 호출 위치는 상위 스코프에 아무 영향도 주지 않는다
- 그래서 중첩 함수는 바깥 함수의 변수에 접근할 수 있고, 바깥 함수 안에서 호출만 된 함수(정의는 밖에서 한 함수)는 바깥 함수의 변수에 접근할 수 없다

### 함수 객체의 내부 슬롯 [[Environment]]

왜 필요한가

- 함수가 정의된 곳과 호출되는 곳은 다를 수 있음
- 그래도 렉시컬 스코프가 지켜지려면, 함수가 호출되는 곳과 상관없이 자기가 정의된 환경을 기억하고 있어야 함
- 그래서 함수 객체는 내부 슬롯 [[Environment]]에 상위 스코프의 참조를 저장

무엇이 저장되나

- 함수 객체가 만들어지는 시점에 실행 중인 실행 컨텍스트의 렉시컬 환경이 저장됨
- 함수 객체가 만들어지는 시점은 곧 상위 코드가 평가되거나 실행되는 중이므로, 그때 실행 중인 컨텍스트가 바로 상위 코드의 컨텍스트

호출되면 어떻게 쓰이나

- 함수가 호출되면 새 함수 렉시컬 환경이 만들어짐
- 그 외부 참조에 [[Environment]]에 저장된 값이 들어감

### 클로저와 렉시컬 환경

현상

- 바깥 함수가 중첩 함수를 반환하고 끝남
- 바깥 함수의 실행 컨텍스트는 스택에서 pop되었으니, 바깥 함수의 지역 변수도 함께 사라진 것처럼 보임
- 그런데 반환된 중첩 함수를 나중에 호출하면, 이미 끝난 바깥 함수의 지역 변수를 여전히 참조할 수 있음

원리
| 단계 | 일어나는 일 |
| --- | --- |
| 1. 바깥 함수 객체 생성 | 바같 함수의 [[Environment]] = 전역 렉시컬 환경 |
| 2. 바깥 함수 호출 | 바깥 함수 렉시컬 환경 생성. 외부 참조 = 전역 렉시컬 환경 |
| 3. 중첩 함수 객체 생성 | 중첩 함수의 [[Environment]] = 바깥 함수 렉시컬 환경 |
| 4. 중첩 함수 반환, 바깥 함수 종료 | 바깥 함수 실행 컨텍스트는 pop. 그러나 바깥 함수 렉시컬 환경은 남음 |
| 5. 반환된 함수 호출 | 새 렉시컬 환경의 외부 참조 = [[Environment]] = 바깥 함수 렉시컬 환경 -> 바깥 함수의 변수를 찾을 수 있음 |

4단계에서 렉시컬 환경이 남는 이유:

- 바깥 함수 렉시컬 환경을 중첩 함수의 [[Environment]]가 참조하고 있음
- 그 중첩 함수는 바깥에서 변수 등으로 참조되고 있음
- 가비지 컬렉터는 누군가 참조하고 있는 메모리를 해제하지 않음

### 클로저의 정의

- 바깥 함수보다 중첩 함수가 더 오래 살아남아서, 이미 끝난 바깥 함수의 변수를 참조할 수 있을 때 그 중첩 함수를 클로저라고 한다
- 중첩 함수는 바깥 함수가 살아 있는지(실행 컨텍스트가 있는지)와 상관없이, 자신이 정의된 위치로 정해진 상위 스코프를 기억한다. 그래서 상위 스코프의 식별자를 참조할 수 있고, 값을 바꿀 수도 있다

모든 함수가 클로저인가?

- 모든 함수는 상위 스코프를 기억하고 있으니 이론적으로는 모든 함수가 클로저
- 하지만 일반적으로는 다음 두 조건을 모두 만족할 때만 클로저라고 부름
  | 경우 | 상위 식별자 참조 | 바깥보다 오래 생존 | 클로저인가 |
  | -- | -- | -- | -- |
  | 상위 스코프의 식별자를 하나도 참조하지 않는 중첩 함수 | X | O | 아니다 |
  | 상위 식별자를 참조하지만 바깥 함수안에서 호출되고 끝나는 중첩 함수 | O | X | 일반적으로 아님(바깥보다 먼저 사라지므로 클로저의 본질에 맞지 않음 |
  | 상위 식별자를 참조하고, 반환되어 바깥보다 오래 사는 중첩 함수 | O | O | 클로저 |

자유 변수

- 클로저가 참조하는 상위 스코프의 변수를 자유 변수(free variable)라고 한다
- 클로저라는 말은 "함수가 자유 변수에 대해 닫혀 있다(closed)"는 뜻. 풀어 말하면 "자유 변수에 묶여 있는 함수"

메모리 걱정

- 모던 엔진은 상위 스코프 중에서 클로저가 실제로 참조하는 식별자만 기억함
- 필요한 것을 기억하는 것이므로 불필요한 메모리 낭비로 볼 수 없음

### 클로저의 활용

목적

- 클로저는 상태(state)를 안전하게 바꾸고 유지하기 위해 씀
- 상태가 의도치 않게 바뀌지 않도록 안전하게 은닉하고, 특정 함수에게만 상태 변경을 허용함

상태를 어디에 둘지 비교(카운터 예시)
| 상태를 두는 곳 | 문제 |
| --- | -- |
| 전역 변수 | 누구나 접근하고 바꿀 수 있다. 의도치 않은 변경이 오류로 이어진다 |
| 함수의 지역 변수 | 외부 접근은 막히지만, 호출할 때마다 다시 선언되고 초기화되어 이전 상태를 유지하지 못한다 |
| 즉시 실행 함수의 지역 변수 + 반환된 클로저 | 즉식 실행 함수는 한 번만 실행되므로 초기화는 한 번 뿐이다. 변수는 밖에서 접근할 수 없고, 반환된 클로저만 읽고 바꿀 수 있다 -> 해결 |

### 캡슐화와 정보 은닉

캡슐화: 객체의 상태와 그 상태를 다루는 동작을 하나로 묶은 것
정보 은닉: 캡슐화를 통해 공개할 필요가 없는 구현을 외부에서 감추는 것. 부적절한 접근으로 상태가 바뀌는 것을 막고, 객체 간 결합도를 낮춤
