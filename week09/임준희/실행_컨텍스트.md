### 실행 컨텍스트

- 실행 컨텍스트는 소스코드를 실행하는 데 필요한 환경을 제공하고, 코드의 실행 결과를 실제로 관리하는 영역이다
- 실행 컨텍스트를 이해하면 다음 내용을 이해할 수 있다
  - 스코프를 기반으로 식별자와 값을 관리하는 방식
  - 호이스팅이 생기는 이유
  - 클로저의 동작 방식
  - 태스크 큐와 함께 동작하는 이벤트 핸들러, 비동기 처리

### 소스코드의 타입

ECMAScript 사양은 소스코드를 4가지로 나누고, 4가지 모두 실행 컨텍스트를 만든다
| 타입 | 범위 | 만드는 것 |
| -- | -- | -- |
| 전역 코드 | 전역에 존재하는 코드. 전역에 정의된 함수, 클래스의 내부 코드는 제외 | 전역 실행 컨텍스트 |
| 함수 코드 | 함수 내부 코드. 중첩된 함수, 클래스의 내부 코드는 제외 | 함수 실행 컨텍스트 |
| eval 코드 | 빌트인 전역 함수 eval에 인수로 넘겨져 실행되는 코드 | eval 실행 컨텍스트 |
| 모듈 코드 | 모듈 내부 코드. 모듈 안의 함수, 클래스 내부 코드는 제외 |

- 함수 안에 함수가 있으면 바깥 함수의 코드와 안쪽 함수의 코드는 서로 다른 함수 코드다. 그래서 각자 호출될 때마다 따로 실행 컨텍스트를 만든다

왜 4가지로 나누나?
타입마다 실행 컨텍스트를 만드는 과정과 관리하는 내용이 다르기 때문

- 전역 코드
  - 전역 변수를 관리할 최상위 스코프(전역 스코프)를 만들어야 한다
  - var로 선언한 전역 변수와 함수 선언문으로 정의한 전역 함수를 전역 객체의 프로퍼티와 메서드로 바인딩해야 한다
  - 그래서 전역 객체와 연결되어야 한다
- 함수 코드
  - 지역 스코프를 만들고 지역 변수, 매개변수, arguments 객체를 관리해야 한다
  - 이 지역 스코프를 전역 스코프에서 시작하는 스코프 체인에 연결해야 한다
- eval 코드
  - strict mode에서 자기만의 독자적인 스코프를 만든다
- 모듈 코드
  - 모듈마다 독립적인 모듈 스코프를 만든다

### 소스코드의 평가와 실행

엔진은 모든 소스코드를 두 단계로 나눠 처리한다.

1. 평가: 실행 컨텍스트를 만들고 변수, 함수 등의 선언문만 먼저 처리해서 식별자를 실행 컨텍스트가 관리하는 스코프에 등록한다
2. 실행: 선언문을 뺀 나머지 문을 순서대로 실행한다(런타임). 필요한 식별자는 스코프에서 찾아 쓰고, 실행 결과는 다시 스코프에 등록한다

var x;
x = 1;

1. 평가: var x;가 먼저 처리된다. 식별자 x가 스코프에 등록되고 undefined로 초기화된다
   | 실행 컨텍스트 | |
   | --- | --- |
   | x | undefined |
2. 실행: var x;는 평가 단계에서 이미 끝났으므로 x = 1;만 실행된다 - 값을 할당하기 전에 x가 선언된 변수인지, 즉 실행 컨텍스트의 스코프에 x가 등록되어 있는지 먼저 확인한다 - 등록되어 있으면 값을 할당하고, 그 결과를 실행 컨텍스트에 등록한다
   | 실행 컨텍스트 | |
   | --- | --- |
   | x | 1 |

- 호이스팅은 별도의 기능이 아니라 이 두 단계 구조에서 나오는 결과다. 선언이 실행보다 먼저 처리되니 선언문보다 위에서도 식별자가 이미 존재한다

### 실행 컨텍스트의 역할

```js
// 전역 변수 선언
const x = 1;
const y = 2;

// 함수 정의
function foo(a) {
  // 지역 변수 선언
  const x = 10;
  const y = 20;

  // 메서드 호출
  console.log(a + x + y); // 130
}

// 함수 호출
foo(100);

// 메서드 호출
console.log(x + y); // 3
```

엔진이 코드를 처리하는 순서

1. 전역 코드 평가
   - 전역 코드의 변수 선언문과 함수 선언문을 먼저 처리한다
   - 이렇게 생긴 전역 변수와 전역 함수가 실행 컨택스트의 전역 스코프에 등록된다
   - var 전역 변수와 함수 선언문 전역 함수는 전역 객체의 프로퍼티와 메서드가 된다
2. 전역 코드 실행
   - 런타임이 시작되어 전역 변수에 값이 할당되고 함수가 호출된다
   - 함수가 호출되면 전역 코드 실행을 일시 중단하고 함수 내부로 들어간다
3. 함수 코드 평가
   - 매개변수와 지역 변수 선언문을 먼저 처리해서 지역 스코프에 등록한다
   - arguments 객체가 만들어져 지역 스코프에 등록되고, this 바인딩도 결정된다
4. 함수 코드 실행
   - 매개변수와 지역 변수에 값이 할당되고 console.log가 호출된다
   - console 식별자는 스코프 체인으로 찾는다. 지역 스코프에서 전역 스코프로 올라간다
   - console은 스코프에 등록된 변수가 아니라 전역 객체의 프로퍼티다. 즉 전역 객체의 프로퍼티도 전역 변수처럼 전역 스코프를 통해 찾을 수 있어야 한다
   - log는 console 객체의 프로토타입 체인으로 찾는다
   - 인수 a + x + y를 평가한다. 각 식별자는 스코프 체인으로 찾는다
   - console.log가 끝나면 함수 코드 실행이 끝나고, 호출 전으로 돌아가 전역 코드 실행을 이어 간다

코드가 실행되려면 관리해야 하는 것

1. 선언으로 생긴 모든 식별자(변수, 함수, 클래스 등)를 스코프별로 등록하고, 바인딩된 값의 변화를 계속 관리해야 한다
2. 스코프는 중첩 관계에 따라 스코프 체인을 이뤄야 한다. 그래야 스코프 체인을 따라 상위 스코프로 올라가며 식별자를 찾을 수 있다
3. 현재 실행 중인 코드의 실행 순서를 바꿀 수 있어야 하고(함수 호출), 다시 원래 자리로 돌아갈 수도 있어야 한다
   이걸 전부 관리하는 것이 실행 컨텍스트다.

- 실행 컨텍스트는 식별자를 등록하고 관리하는 스코프, 그리고 코드 실행 순서 관리를 구현한 내부 메커니즘이다. 모든 코드는 실행 컨텍스트를 통해 실행되고 관리된다
  | 관리 대상 | 담당 |
  | --- | --- |
  | 식별자, 스코프 | 실행 컨텍스트의 렉시컬 환경 |
  | 코드 실행 순서 | 실행 컨텍스트 스택 |

### 실행 컨텍스트 스택

```js
const x = 1;

function foo() {
  const y = 2;

  function bar() {
    const z = 3;
    console.log(x + y + z);
  }
  bar();
}

foo(); // 6
```

- 엔진은 전역 코드를 평가해서 전역 실행 컨텍스트를 만들고, 함수가 호출되면 함수 코드를 평가해서 함수 실행 컨텍스트를 만든다
- 이렇게 만든 실행 컨텍스트들은 스택 자료구조로 관리된다. 이것이 실행 컨텍스트 스택(콜 스택)이다.

1. 전역 코드의 평가와 실행
   - 전역 코드를 평가해서 전역 실행 컨텍스트를 만들고 스택에 push한다
   - 전역 변수 x와 전역 함수 foo가 전역 실행 컨텍스트에 등록된다
   - 전역 코드가 실행되어 x에 값이 할당되고 foo가 호출된다
2. foo 함수 코드의 평가와 실행
   - foo가 호출되면 전역 코드 실행이 일시 중단되고, 제어권이 foo 내부로 넘어간다
   - foo 함수 코드를 평가해서 foo 실행 컨텍스트를 만들고 push 한다
   - 지역 변수 y와 중첩 함수 bar가 실행 컨텍스트에 등록된다
   - foo 코드가 실행되어 y에 값이 할당되고 bar가 호출된다
3. bar 함수 코드의 평가와 실행
   - foo 코드 실행이 일시 중단되고 제어권이 bar로 넘어간다
   - bar 실행 컨텍스트를 만들어 push하고, 지역 변수 z를 등록한다
   - z에 값이 할당되고 console.log를 호출한 뒤 bar가 끝난다
   - console.log도 함수라서 호출되면 실행 컨텍스트가 push된다
4. foo 함수 코드로 복귀
   - bar가 끝나면 제어권이 foo로 돌아오고, bar 실행 컨텍스트를 pop한다
   - foo는 더 실행할 코드가 없으므로 끝난다
5. 전역 코드로 복귀
   - foo 실행 컨텍스트를 pop한다. 더 실행할 전역 코드가 없으므로 전역 실행 컨텍스트도 pop한다
   - 스택이 비게 된다

정리

- 실행 컨텍스트 스택은 코드의 실행 순서를 관리한다
- 스택 맨 위에 있는 실행 컨텍스트가 언제나 지금 실행 중인 코드의 실행 컨텍스트다.

스택은 항상 단순 LIFO는 아니다

- 제너레이터와 async함수는 await에서 멈출 때 자기 실행 컨텍스트를 스택에서 뺀다. 이때 어디까지 실행했는지를 code evaluation state에 저장해 둔다
- 나중에 Promise가 처리되면 그 컨텍스트를 다시 push해서 이어서 실행한다
- 그래서 "함수가 끝나야 pop된다"는 말은 일반 함수에만 맞는다

### 렉시컬 환경

- 렉시컬 환경은 식별자, 식별자에 바인딩된 값, 그리고 상위 스코프에 대한 참조를 기록하는 자료구조다
- 실행 컨텍스트 스택이 코드의 실행 순서를 관리한다면, 렉시컬 환경은 스코프와 식별자를 관리한다
- 키와 값을 갖는 객체 형태의 스코프를 만들어 식별자를 키로 등록하고, 바인딩된 값을 관리한다
- 즉 렉시컬 환경은 스코프를 구분해서 식별자를 등록하고 관리하는 저장소이자 렉시컬 스코프의 실체다

```js
const x = 1;

function foo() {
  const y = 2;
  console.log(x + y);
}
```

| 렉시컬 환경                | 식별자 | 값              | outer                      |
| -------------------------- | ------ | --------------- | -------------------------- |
| foo Lexical Environment    | y      | 2               | Global Lexical Environment |
| Global Lexical Environment | x      | 1               | null                       |
|                            | foo    | function object |                            |

실행 컨텍스트의 두 컴포넌트
| 실행 컨텍스트의 컴포넌트 | 역할|
| --- | --- |
| VariableEnvironment | var 선언을 등록할 상자를 가리킨다. 함수가 끝날 때까지 움직이지 않는다 |
| LexicalEnvironment와 | let/const 선언을 등록하고, 식별자를 검색하기 시작할 상자를 가리킨다. 블록에 들어가고 나올 때마다 움직인다 |

- 처음 만들어질 때는 LexicalEnvironment와 VariableEnvironment가 같은 렉시컬 환경을 가리킨다
- 몇 가지 상황을 만나면 VariableEnvironment용 렉시컬 환경을 새로 만든다. 그때부터 둘의 내용이 달라질 수 있다

렉시컬 환경의 구성
| 구성 요소 | 역할 |
| --- | --- |
| 환경 레코드(Environment Record) | 스코프에 포함된 식별자를 등록하고, 바인딩된 값을 관리하는 저장소. 소스코드 타입에 따라 관리하는 내용이 다르다 |
| 외부 렉시컬 환경에 대한 참조 (Outer Lexical Environment Reference) | 상위 스코프를 가리킨다. 상위 스코프는 해당 실행 컨텍스트를 만든 소스코드를 포함하는 상위 코드의 렉시컬 환경이다. 이 참조로 단방향 링크드 리스트인 스코프 체인이 만들어진다|

### 실행 컨텍스트의 생성과 식별자 검색 과정

1. 전역 객체 생성

- 전역 코드를 평가하기 전에 만들어 진다
- 빌트인 전역 프로퍼티와 함수, 표준 빌트인 객체, 호스트 객체(Web API 등)를 가진다

2. 전역 코드 평가
   - 전역 실행 컨텍스트를 만들어 스택에 push
   - 전역 환경 레코드 생성, this 바인딩, 외부 렉시컬 환경에 대한 참조 결정을 통해 전역 렉시컬 환경을 만든다

3. 전역 코드 실행
   - 선언문을 뺀 나머지가 순서대로 실행된다. 변수에 값이 할당되고 함수가 호출됨
   - 함수를 호출하면 전역 코드 실행을 일시 중단하고 제어권이 함수로 넘어간다
   - 식별자 결정
     - 같은 이름의 식별자가 여러 스코프에 있을 수 있으므로, 어느 스코프의 것을 쓸지 정해야 한다
     - 검색을 항상 실행 중인 실행 컨텍스트의 렉시컬 환경에서 시작
     - 못 찾으면 외부 참조를 따라 상위 렉시컬 환경으로 올라감
     - 전역까지 올라가도 못 찾으면 ReferenceError

4. 함수 코드 평가
   - 함수 실행 컨텍스트를 만든다
   - 함수 렉시컬 환경을 만든다

5. 함수 코드 실행
   - 지역 변수에 값이 할당되고 문이 순서대로 실행됨
   - 식별자 검색은 지금 실행 중인 함수의 렉시컬 환경에서 시작
   - 상위 스코프에 같은 이름이 있어도 가까운 쪽이 먼저 찾아짐

6. 함수 종료
   - 실행 컨텍스트가 스택에서 pop되고, 바로 아래 컨텍스트가 다시 실행 중인 실행 컨텍스트가 된다
   - 렉시컬 환경은 같이 사라지지 않을 수 있음
     - 렉시컬 환경은 실행 컨텍스트와 별개인 독립 객체
     - 누군가 참조하고 있으면 GC 대상이 되지 않고 남음
     - 이것이 클로저가 가능한 이유

7. 전역 코드 종료
   - 더 실행할 코드가 없으면 전역 실행 컨텍스트도 pop되어 스택이 빈다
