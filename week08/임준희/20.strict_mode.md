### strict mode

- ES5(2009)에서 추가된 실행 규칙
- 같은 코드를 더 엄격한 규칙으로 해석
- strict mode code와 non-strict code 두 종류로 나누고, 여러 알고리즘이 "strict면 에러, 아니면 조용히 넘어감"으로 갈라짐

### 언제 strict 모드가 되나

| 코드          | strict가 되는 조건                                                |
| ------------- | ----------------------------------------------------------------- |
| 스크립트 전체 | 선두에 'use strict';                                              |
| 함수          | 함수 몸체 선두에 'use strict'; 또는 strict 코드 안에 들어 있을 때 |
| 모듈          | 항상 strict. 지시어 필요 없음                                     |
| 클래스        | 클래스 몸체 전체가 항상 strict                                    |
| eval 코드     | 선두에 지시어가 있거나, strict 코드 안에서 직접 호출된 eval       |

### 'use strict'의 정확한 규칙

- 스크립트나 함수 몸체의 맨 앞에 오는 "문자열 리터럴만으로 된 문장"들의 연속을 Directive Prologue라 한다. 그 안에 정확히 'use strict' 또는 "use strict"가 있으면 strict가 된다.
- 다른 문이 한 번이라도 나오면 Prologue는 거기서 끝난다. 그 뒤의 'use strict'는 그냥 문자열 표현식일 뿐이다.
- 앞에 다른 문자열 문장이 있어도 된다. 'foo'; 'use strict'; 가능

### 스크립트 단위로 적용된다

- 한 스크립트의 'use strict'는 다른 스크립트에 영향을 주지 않는다.
- 책은 그래서 즉시 실행 함수로 감싸라고 한다. 실무에서는 이 조언이 거의 필요 없다.
- import/export를 쓰는 파일은 모듈이라 항상 strict고, 클래스 안도 항상 strict다.

### strict mode가 발생시키는 에러

- 선언하지 않은 변수에 값을 할당하면 ReferenceError (non-strict는 전역 객체에 프로퍼티를 만들고 넘어감)
- delete 연산자로 변수, 함수, 매개변수를 삭제하면 SyntaxError
- 중복된 매개변수 이름을 사용하면 SyntaxError
- with문을 사용하면 SyntaxError

### strict mode 적용에 의한 변화

- 함수를 일반 함수로 호출하면 this에 undefined가 바인딩
- 매개변수에 전달된 인수를 재할당해서 변경해도 arguments 객체에 반영되지 않음

### 왜 모듈과 클래스는 강제 strict인가

strict mode를 일반 함수와 스크립트에 강제로 적용하면, 그 규칙을 모르고 작성된 예전 웹사이트들이 브라우저 업데이트 후 에러를 내며 동작을 멈추게 돼서 opt-in으로 만들었다. 반면 class와 모듈은 ES6에서 새로 생긴 문법이라 영향받을 예전 코드가 없으니 처음부터 strict를 강제할 수 있었다.

### 왜 지시어가 문자열 리터럴인가

'use strict'가 키워드가 아니라 문자열 리터럴인 이유는 ES5 이전 브라우저가 그 줄을 "값을 버리는 표현식 문"으로 보고 에러 없이 무시하게 하기 위해서다. 새 키워드였다면 옛 브라우저에서 SyntaxError가 나서 파일 전체가 멈췄을 것이다. 대신 문자열은 아무 데나 올 수 있어서, 파서가 지시어로 인식하는 범위를 몸체 맨 앞의 Directive Prologue로 제한하게 됐다.
