### var의 문제점

1. 중복 선언 허용: 같은 스코프에서 var x를 여러 번 써도 에러가 없다. 이미 있는 변수를 모르고 중복 선언하면 값이 조용히 덮인다.
2. 함수 레벨 스코프: 함수 코드 블록만 스코프로 인정한다. if, for 안의 var는 전부 함수나 전역 변수가 된다.
3. 호이스팅: 선언문 이전에 참조해도 에러가 아니라 undefined다. 흐름상 맞지 않고 가독성을 떨어뜨린다.

### let

1. 중복 선언 금지: 같은 스코프에 같은 이름을 다시 선언하면 SyntaxError.
2. 블록 레벨 스코프: 모든 코드 블록이 스코프다. 함수 안의 블록 스코프는 함수 스코프에 중첩된다.
3. 호이스팅: let도 호이스팅된다. 다만 선언 단계와 초기화 단계가 분리된다. 스코프 진입 시 선언은 되지만 초기화는 선언문에 도달해야 일어나고, 그 사이가 TDZ다. TDZ에서 접근하면 ReferenceError가 난다.

### const

1. 선언과 동시에 초기화: const foo;는 SyntaxError. 초기화 없이는 영원히 TDZ라 의미가 없기 때문
2. const는 재할당만 막는다. 객체를 넣으면 프로퍼티 추가, 삭제, 변경은 된다. 변수가 가리키는 참조가 안 바뀔 뿐 객체 내용은 바뀐다.

### TDZ는 왜 필요했나?

TDZ를 만든 이유는 const 때문이다. let은 TDZ 없이도 정의할 수 있었다.
const의 약속은 "이 이름은 한 번 값을 가지면 끝까지 그 값이다"이다. 그런데 var 방식으로 선언 전 접근을 허용하면 이렇게 된다.

```javaScript
console.log(x); // undefined
const x = 1;
console.log(x); // 1
```

x가 undefined였다가 1이 된다. 값이 바뀐것이고 상수가 아니다. 선언 전 접근을 허용하는 순간 const의 정의가 깨진다.
선택지는 두 가지였을 것 같다.

1. 선언 전 접근을 에러로 만든다 -> TDZ
2. const를 호이스팅 하지 않는다 -> 그러면 같은 스코프에서 const x보다 위에 있는 코드가 바깥 스코프의 x를 보게 되어, 한 스코프 안에서 같은 이름이 다른 걸 가리키는 상황이 생긴다.
   사양은 첫 번째를 골라서 이름은 스코프 진입 시 등록하되(호이스팅), 선언문에 도달하기 전 접근은 에러로 했다.
