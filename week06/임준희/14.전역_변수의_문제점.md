### 지역 변수

- 변수는 선언으로 생성되고, 할당으로 값을 갖고, 언젠가 소멸한다. 생명 주기가 없다면 한 번 선언된 변수가 프로그램 종료까지 메모리를 차지하게 된다.
- 함수 안에서 선언한 지역 변수는 함수가 호출될 때 생성되고 함수가 종료되면 소멸한다.
- 호이스팅은 스코프 단위로 동작한다. 전역 변수는 전역 코드 실행 전에, 함수 안의 변수는 함수 호출 직후 본문 실행 전에 등록된다.
- 지역 변수의 생명 주기는 함수의 생명 주기와 대부분 일치한다. 예외는 누군가 그 스코프를 참조하고 있을 때(클로저), 함수가 끝나도 스코프가 살아남는다.
- 할당된 메모리는 아무도 참조하지 않을 때 가비지 컬렉터가 해제한다. 스코프도 같다.

### 전역 변수

- 전역 코드는 명시적 진입점 없이 로드되자마자 실행되고, 마지막 문이 끝나면 종료된다.
- var로 선언한 전역 변수는 전역 객체의 프로퍼티가 된다. 그래서 생명 주기가 전역 객체와 같고, 브라우저에서는 페이지를 닫을 때까지 살아 있다.

### 전역 변수의 문제점

1. 암묵적 결합: 모든 코드가 참조하고 바꿀 수 있다. 유효 범위가 클수록 가독성이 떨어지고 의도치 않게 상태가 바뀔 위험이 커진다.
2. 긴 생명 주기: 메모리를 오래 차지하고, 상태를 바꿀 기회도 많다. var는 중복 선언을 허용하므로 이름이 겹치면 재할당이 조용히 일어난다.
3. 스코프 체인의 종점: 식별자를 찾을 때 가장 마지막에 검색된다.
4. 네임스페이스 오염: 파일이 나뉘어 있어도 전역 스코프는 하나다. 다른 파일의 같은 이름 전역 변수나 함수와 충돌한다.

### 전역 변수 사용을 억제하는 방법

변수의 스코프는 좁을수록 좋다. 전역 변수를 절대 쓰지 말라는 게 아니라 남발하지 말라는 것이다.

1. 즉시 실행 함수(IIFE): 코드를 (function(){...}())로 감싸면 안의 var는 전부 그 함수의 지역 변수가 된다. 라이브러리에서 많이 쓰던 방식
2. 네임스페이스 객체: var MYAPP = {}처럼 하나만 전역에 두고 나머지는 그 프로퍼티로 넣는다. 충돌은 막지만 MYAPP 자체가 전역이라 그다지 유용하지 않다.
3. 모듈 패턴: IIFE가 객체를 반환하게 한다. 반환 객체에 넣은 것만 외부에 노출되고, 안의 변수는 밖에서 접근 불가능하다. 클로저 기반이고 캡슐화, 정보 은닉까지 가능하다.
4. ES6 모듈: 파일마다 독자적인 모듈 스코프를 갖는다. 모듈 안의 var는 전역 변수도, window의 프로퍼티도 아니다.

### 정보 은닉 세 가지 방식

```JavaScript
// 1) 모듈 패턴: 스코프로 숨김
const Counter1 = (function(){
    var num = 0;
    return {
        increase(){
            return ++num
        },
        decrease(){
            return --num
        }}
})()

// 2) 클래스 #private: 객체의 프라이빗 이름으로 숨김(ES2022)
class Counter2 {
    #num = 0;
    increase() { return ++this.#num }
    decrease() { return --this.#num }
}

// 3) ES모듈: export 안 해서 숨김
let num3 = 0;
export function increase3() { return ++num3 }
```

1. 모듈 패턴

- num이 어디에 있나: IIFE의 Environment Record
- 밖에서 어떻게 막히나: 그 스코프에 접근할 식별자가 없음. 반환 객체에는 num이라는 프로퍼티 자체가 없음

2. #private

- num이 어디에 있나: 인스턴스 안에 있다. 단 [[PrivateElements]]라는 별도 내부 슬롯
- 밖에서 어떻게 막히나: #num은 문자열 키가 아니라 클래스 본문 안에서만 쓸 수 있는 Private Name으로 밖에서 .#num은 문법 에러

3. ES모듈

- num이 어디에 있나: 모듈의 Module Environment Record
- 밖에서 어떻게 막히나: export 안 한 바인딩은 import 불가

모듈 패턴은 클로저 그 자체다. increase 함수가 [[Environment]]로 IIFE의 레코드를 잡고 있어서 IIFE가 끝나도 num이 살아 있고, 그 레코드에 닿을 수 있는 건 그 함수들 뿐이다. 단점은 인스턴스를 여러개 만들기 어렵다는 것

#private은 책이 "자바스크립트에는 접근 제한자가 없다"고 쓴 뒤에 생긴 기능이다. #num은 프로퍼티가 아니다. 사양에서 Private Name이라는 별도 종류로, 객체의 프로퍼티 목록에 전혀 나타나지 안혹, 클래스 본문 밖에서는 #num이라는 토큰 자체가 파싱 단계에서 거부된다. 그래서 런타임 에러가 아니라 SyntaxError가 난다.

ES모듈은 파일이 곧 스코프다. 최상위 let num3는 그 파일의 Module Environment Record에 있고, export 목록에 없으면 밖에서 이름을 부를 방법이 없다. 모듈 패턴의 IIFE가 하던 일을 언어가 파일 단위로 대신 해 주는 것이다.

### var 전역 변수는 globalThis에 붙는데, let/const는 왜 안 붙나?

함수 스코프는 Environment Record가 하나다. 전역 스코프는 Environment Record가 두개고, 사양은 이 둘을 묶어 Global Environment Record라고 부른다.
하나는 Object Environment Record다. 이건 변수를 따로 저장하지 않고, 지정된 객체의 프로퍼티를 바인딩으로 쓴다. 전역의 경우 그 객체가 전역 객체다. 그래서 여기에 바인딩을 만든다는 건 전역 객체에 프로퍼티를 만든다는 뜻이고, 바인딩을 읽는다는 건 전역 객체의 프로퍼티를 읽는다는 뜻이다. 'var'와 함수 선언문은 이 Object Environment Record에 들어간다.

다른 하나는 Declarative Environment Record다. 함수 안의 변수를 담는 것과 같은 종류로, 전역 객체와 아무 관계가 없다. let, const, class는 여기에 들어간다. 그래서 let y = 2를 해도 전역 객체에는 아무 일도 안 일어난다.

```javaScript
var x = 1; // Object Environment Record -> 전역 객체의 프로퍼티 -> globalThis.x === 1
let y = 2; // Declarative Environment Record -> 전역 객체와 무관 -> globalThis.y === undefined
```

이 분리는 전역에서만 일어난다. 함수 안에서는 var, let 함수선언 전부 하나의 Environment Record에 들어간다.

### 클로저가 스코프를 살려 둔다면, 그 스코프의 변수 전부가 남나 아니면 쓰는 것만 남나?

사양: 레코드 전체가 남는다. 함수 객체의 [[Environment]]가 바깥 Environment Record 하나를 통째로 가리키므로, 사양 모델에서는 그 레코드에 등록된 모든 바인딩이 함께 살아 있다. 사양에선 메모리 얘기가 없어서 뭘 버리는지는 모른다.

V8: 클로저가 실제로 참조하는 변수만 힙의 Context 객체에 올리고, 나머지는 스택 레지스터에 둬서 함수가 끝나면 사라진다. 파싱 단계에서 안쪽 함수가 어떤 바깥 변수를 쓰는지 알 수 있기 때문이다.
